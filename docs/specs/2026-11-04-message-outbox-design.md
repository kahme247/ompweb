# Message outbox: omp-web holds every message until omp has it — design

Date: 2026-11-04. Status: proposed, not implemented.
Builds on: `docs/specs/2026-11-01-browser-link-design.md` (sequenced lines, `rid` dedupe), `docs/specs/2026-10-31-websocket-link-design.md` (host link seq/ack, outbox, hello), `docs/specs/2026-10-28-remote-hosts-design.md` ("Transport down is not exited").
Replaces, once shipped: the composer's "Sending…" row (`sendQueued` in `components/ChatInput.tsx`).

## Why

When a message cannot reach omp, the user finds out late and in the wrong place. Today:

- A prompt sent while idle shows an optimistic bubble that disappears on failure; a follow-up or steer sent during a run shows nothing in the transcript. While a remote host is offline the send waits for a 503 that can take seconds (`transport_unavailable` after 15 s on the browser link), and then the text drops back into the composer.
- The composer is the only place a refused message survives, so the user has to wait for the answer before typing the next thing.
- An outcome of `delivery: "unknown"` (the link dropped after the command left) drops the draft so it is never sent twice, and the message may be lost.

The outbox moves ownership: after the browser commits a submitted message, omp-web retains it across tab closure, reconnects, web-server restarts and host outages until acceptance is confirmed or an explicit failure remains visible. The composer clears only after that local commit. Retries reuse the message ID and do not independently resend uncertain host commands; the native protocol's limits on proving acceptance are explicit in O5.

## Decisions

### O1. What the user sees

- Every submitted message (an idle prompt, a follow-up, a steer) appears at once as a **held bubble** at the end of the transcript, after the live turn: dimmed (`--text-muted` on `--user-bg` at reduced opacity), with a spinner and a status line naming the leg it is stuck on, as chat apps do:
  - **Sending**: the browser has it; the web server has not confirmed it yet (offline phone, web server restarting).
  - **Waiting for <host>** (clock icon): the web server has it; the host is offline. It goes when the host links again.
  - **Delivering**: dispatched to the host, waiting for omp's answer.
  - **Not sent** (alert icon, no spinner): it cannot go by itself (O6). It remains visible with **Delete** available. Transient failures retry on their own, without a button.
- Held bubbles are ordered by submission. Each has an informational mode label (Prompt / Follow-up / Steer); phase 1 adds no mode-changing controls.
- For a confirmed server-held entry, hand-off waits for omp's reply and its replacing user message or queue frame (O4). Browser/server copies merge by outbox ID. Recovery of old unconfirmed browser entries outside the bounded settled-ID snapshot follows O2 rather than inferring delivery from missing IDs.
- A confirmed server-held or failed bubble offers **Delete**; a permanently refused browser-local entry does too. **Sending** and **Delivering** have no withdrawal actions. Browser-local deletion waits for IndexedDB commit before removing the row; a failed transaction leaves the message visible. An uncertain-delivery confirmation states that the message may already have reached omp or could still arrive: deleting its tracking record does not undo or cancel native work.
- **Server-held Delete is idempotent by message ID.** `outbox_remove {id}` checks the session and retires an eligible entry transactionally before replying `{success:true,data:{removed:true,entry}}`. Keep its tombstone for eight days so a late `outbox_add` cannot recreate it. Repeated removal of an already absent or settled entry returns `{success:true,data:{removed:false}}`; it does not restore or dispatch anything. If dispatch won the race, answer `409 outbox_dispatched`. The client does not optimistically erase a server-held bubble: reconcile through authoritative `outbox_update`/state and settled IDs. A lost response is an uncertain deletion, not success or cancellation; retain the last known state, surface the error, and allow the same-ID command to be retried or safely replayed by the link.
- **Delayed acknowledgement does not own newer input.** Clear only the submitted draft's unchanged content and edit generation after browser storage commits. Clearing and retyping identical text is a newer edit, not an unchanged draft. Preserve this distinction across remounts and confirmed identity moves while still consuming an untouched originating draft.
- Every tab and device viewing the session sees the held bubbles the web server has (O2); a message still on its first leg shows only in the browser that sent it, as in any chat app. This is the one exception to "Never track chips client-side" in `AGENTS.md`: the outbox holds only what omp does not have yet, and omp's queue stays omp's.

### O2. Where the outbox lives

- **Browser (first leg).** Two outboxes, one per leg, keyed by the same message id. The browser's is owned by the event-stream worker (`lib/event-stream-worker.ts`), not by a tab or a composer: it already outlives tab switches and chat switches and already resends link lines. Each entry (id, session or chat id, scope, Advisor boolean, mode, text, images, upload ids and proofs, draft key, created) is written to IndexedDB **before** the composer clears, so a reload, a closed tab or a crashed browser does not lose it: the next worker to start resends whatever IndexedDB still holds. The id is `Math.random().toString(36).slice(2, 12) + Date.now().toString(36)`, as the worker's other ids. The worker sends `outbox_add {id, scope, mode, message, images?, uploads?, uploadProofs?}` for the session over its current transport (the browser link's `cmd`, resent after a resume, or `POST /api/agent/[id]` in SSE mode), retrying transient failures with back-off, and deletes the IndexedDB entry only when the server answers that it stored it. Tabs merge their browser entries with the server's `outbox_update` by id; a retained delivered tombstone in the add response removes an unconfirmed browser copy without dispatching it again.
- **Existing-session Advisor intent.** Capture the effective `advisor` boolean, including `false`, with each browser entry at Send; retain it through IndexedDB reload, reconnect, keepalive and Background Sync without rereading later browser preferences. Replay carries it through the existing browser-link envelope or HTTP `?advisor=1` query (absence means `false`), not the message body. Server acceptance snapshots that value in SQLite, and dispatch passes it through the existing session-start/idle-replacement path; a busy child keeps the existing Advisor replacement rules. This contract applies to saved sessions, independently of O7's future new-chat launch configuration.
- **Durable enqueue order and uniqueness.** Allocate a monotonic sequence and insert the new ID in one IndexedDB read-write transaction. Order heads, reloads and Background Sync by that sequence rather than random IDs or tied wall-clock timestamps. A duplicate active ID fails without overwriting its original message; transport retries reuse the existing entry. Legacy entries remain readable through a deterministic fallback. [Transactions serialize access to the same store](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction); [`add()` is insert-only and requires transaction completion for success](https://developer.mozilla.org/en-US/docs/Web/API/IDBObjectStore/add).
- **Bounded acceptance.** Keep the per-session 16 MiB active-payload budget, combining registry aliases, below the browser link's 32 MiB backlog limit. Also bound the total server-held pool to 256 MiB and 1,000 active rows across sessions, including failed entries. Enforce all limits atomically before accepting a new ID; known-ID replay still returns its receipt when the pool is full. Overflow answers `429 outbox_full`: the message remains durable in the browser and retries as accepted entries drain. Never discard already accepted messages to make room. The existing per-command size limit still answers 413.
- **Bounded snapshot backlog.** The storage budget alone does not bound repeated full snapshots. While a viewer is behind, coalesce replaceable pending `outbox_update` snapshots per subscription and retain the latest entries and settled IDs instead of serializing each change into the browser link. Drain only when downstream capacity permits; preserve ordered native-event barriers and the held-message-to-echo hand-off. Never replace already sequenced or partially transmitted lines. Genuine nonreplaceable overflow retains the existing resync limits.
- **Idempotence.** `outbox_add` is idempotent by `id` for the browser's retry lifetime. The browser stops resending an entry seven days after creation, marks it **Not sent** ("not confirmed by the server"), and retains it until explicit deletion. The server keeps delivered IDs for eight days, past that limit. This replaces the 10-minute `(session, rid)` dedupe for message sends.
- **An acceptance receipt, not HTTP success alone.** Delete a browser copy only after a valid `success: true` receipt with a matching `data.entry.id` and recognized stored state. A login page, malformed JSON or unrelated 2xx body remains unconfirmed and retries under the same ID. A legitimate canonical session-ID move is allowed in that receipt. Background Sync waits for its deletion transaction to complete; abort or commit failure rejects the sync so the durable record can be retried.
- **Transport.** `outbox_scope`, `outbox_add` and `outbox_remove` are agent commands, answered by `runAgentCommand` (`lib/agent-command.ts`) before any wrapper starts: the browser link's `cmd`, `POST /api/agent/[id]`, the `pagehide` keepalive and the service worker all use the same path. No new route.
- **Browser-link replay classification.** Add `outbox_scope`, `outbox_add` and `outbox_remove` to shared `isIdempotentCommand` handling on both link ends. Replaying `outbox_add` reuses its message ID and original scope, including after server restart or beyond the link's ten-minute non-idempotent-command window; the server outbox owns deduplication. An unconfirmed `transport_lost`/503 result remains retryable with that same durable entry and blocks later sends in its session. Never create a new message ID to recover a link command.
- **Send, then close the tab at once.** The message must still go once a connection is there, without the user reopening anything where the browser allows it. Three layers, each covering what the one before cannot:
  1. **IndexedDB first.** The entry is committed (transaction `complete`) before the composer clears. This takes milliseconds; a tab killed inside that window is the one case that loses the message (the composer's draft, already in `sessionStorage`, survives a reload of that tab, but not a close).
  2. **`pagehide` with unconfirmed entries:** the tab sends the oldest pending entry of each session as `fetch(POST /api/agent/[id], { keepalive: true })`. It never posts later entries of that session concurrently or posts from an incomplete IndexedDB ordering snapshot. Browsers may finish these requests after the page closes; the shared keepalive budget is 64 KiB, so oversized heads and subsequent entries remain durable for Background Sync or the next open page. Repeated IDs are harmless.
  3. **Service worker Background Sync.** Register `omp-outbox` only on a confirmed outbox-capable active worker. An older push-only worker or one still activating is not proof of capability; update/activation and a bounded capability exchange must establish support before relying on it. The capable worker posts retained IndexedDB entries and commits each confirmed deletion. If support cannot be established offline, retain the data until a worker with outbox Background Sync support becomes available or the app opens again; do not report background delivery. Background Sync remains Chromium-only and browser-scheduled.
- The service worker shares the session cookie (same origin), so a sync after the sign-in expired gets 401 and leaves the entries for the next signed-in page.
- **Replay scope.** Browser entries carry a nonsecret installation/credential scope, obtained from `outbox_scope` or normal `/state` hydration as `outboxScope`. It is derived from the existing installation secret and configured authentication credentials, not the rotating login cookie, so ordinary re-login, process restart, binary upgrade and migration retaining the installation data preserve it. `outbox_add` rejects a mismatched scope before storing or dispatching anything. An independent replacement installation at the same origin must use a new installation secret (or rotate the configured scope credentials) before accepting requests; deliberately copying both secret and credentials preserves the same installation identity and cannot be detected as a replacement. Workers and service workers never rewrite an old entry's scope. This is an installation boundary, not a per-process generation.
- **Web server.** Store per-session validated payloads, delivery intent, state and claim metadata in SQLite in omp-web's data directory (beside the notification store; `close(true)` on shutdown, WAL, 0600). It survives a web-server restart. The `session` channel carries `outbox_update {entries}` on subscribe and on changes. A wrapperless held channel also observes the canonical session-registry lifecycle, so an explicit command can attach a newly ready wrapper without waiting for another outbox mutation; observation itself never starts omp.
- **Unknown ownership is not authoritative absence.** After a web restart, an empty session-to-host cache and a successful local-daemon list do not prove that a session on an offline remote host is gone. A lookup miss is permanent only after every currently registered host has supplied a successful list for its current invalidation generation. Offline or undiscovered hosts keep the miss transient (`503 host_offline`, `delivery:"refused"`); a linked host's failed list returns `503 host_sessions_unavailable` and retries through the existing dispatch timer without requiring a new hello. Cached positive mappings remain usable. `outbox_add` may durably accept the validated message while ownership is unresolved, retaining its ID and payload until host discovery resumes. A host hello or retry resolves the owner through the normal resolver, never through a caller-supplied host or local fallback. Malformed IDs and absence confirmed across all hosts remain permanent refusals.
- **Offline hydration.** `GET /api/sessions/[id]/state` includes `outbox: OutboxEntry[]`, `outboxScope`, and `outboxSettledIds` in successful and error responses. Existing HTTP statuses and error fields stay unchanged, including a host-offline 503. A client with held entries subscribes to the session channel even without a running wrapper; neither snapshot retrieval nor subscription starts omp. Updates carry recent settled IDs (latest 256 within eight days), which suppress known settled browser copies. An ID absent from that bounded list is **unconfirmed**, not proof that the server never accepted it. The worker retries the same `outbox_add` ID; the server's full eight-day deduplication record returns its delivered tombstone without redispatch, and the client suppresses that copy when the reply arrives. Until confirmation, an old browser copy outside the snapshot window may temporarily show **Sending** even if its native message is already in the transcript. The bounded display list is not the delivery deduplication store.
- **Held attachments.** The server privately persists validated completed-upload receipts **before acknowledging upload completion**, not only when accepting `outbox_add`. Otherwise a completed attachment whose message is still in the browser would become unrecoverable after a web restart. Receipts retain the original command owner and existing host/session authorization; they are not accepted from caller-supplied receipt data or exposed in `outbox_update`. A later add can resolve those IDs after restart. A missing or expired receipt or staged file fails the entry explicitly rather than sending without its attachment.
- **Completed-upload authority survives ordinary re-login.** Before reporting a modern upload as completed, main commits an opaque, unpredictable per-upload proof with its trusted completion receipt. Completion replies carry `proof`; the browser retains it with the finished attachment and durably submits `uploadProofs: { [uploadId]: proof }` beside the existing upload IDs. Worker reconnect, keepalive and Background Sync forward the same proof without deriving or rebinding it. A proof is an upload-specific capability, not a login cookie or caller-supplied owner.
  Main validates a cross-login proof against the private receipt, current installation/auth scope and existing 24-hour upload lifetime before granting attachment authority. Completion replays reuse the same proof; a cancel, receipt expiry, changed scope, different upload ID or replacement upload cannot inherit it. Preserve original-owner authorization when no proof exists, including legacy receipts; never manufacture proof from a public scope fingerprint or accept browser-supplied receipt/owner metadata.
  On outbox acceptance, privately snapshot each validated upload's original owner and receipt. Later dispatch uses that accepted authority across cookie changes and server restarts, including messages mixing files from before and after re-login, while retaining host/session/file checks and existing preparation fences. Known message-ID replays return their stored acceptance even after the first-leg proof expires. Proofs grant attachment only, not arbitrary start, chunk, cancel or filesystem access, and never appear in public outbox snapshots, logs, daemon messages or omp commands. Missing or invalid authority remains an explicit retained failure, never a prompt without its files.
  Revalidate and capture upload authority in the same immediate transaction that inserts a new outbox entry, after asynchronous lookups. Keep a private completion fingerprint for later preparation; matching owner/name/size/type alone cannot identify a file generation. An upload ID still referenced by a retained entry cannot be repurposed after its canonical registration is canceled or consumed. A canceled attachment may fail visibly, but an older accepted intent must never receive replacement bytes.
  Canonical completion records refresh stale main-side caches, and every attach replay still validates the real file on its daemon. A completed upload cannot regress to a writable replacement under its old proof. Delayed native acknowledgements retire only their captured completion generation, not a newer upload reusing the same ID.
  First proof issuance atomically binds matching already-held legacy receipts. Original-owner preparation establishes that private generation before awaiting other work, so an unchanged legacy file remains usable when a completed-start replay issues its first browser-visible proof.
- **Host.** The host link already delivers a sequenced line exactly once to a running daemon (seq/ack, resend, duplicate drop). The gap is a daemon restart or a reply lost on the way back; O5 closes it.

### O3. Dispatch

- One dispatcher per session on the web server, FIFO. It sends the oldest held entry when the session's host is linked (`isLinkUp`) and the wrapper is ready (started or adopted, handshake done); it starts the wrapper (`get_state`) if none runs. One entry is in flight at a time per session, so order is kept.
- **Ordinary text at dispatch time:** an idle **prompt** goes as `prompt`; a **prompt** whose session is running goes as `follow_up`. **Follow-up** goes as `follow_up`, **steer** as `steer` while running or `follow_up` when idle.
- **Native and extension slash commands retain the prompt path.** Preserve their unexpanded text and submitted mode in both durable legs. In every mode, dispatch a slash command as `prompt`, so omp can invoke its native/extension handler or expand its prompt template instead of queueing the slash text literally. During a run, add `streamingBehavior:"steer"` for Steer intent or `"followUp"` for Prompt/Follow-up intent; when idle, omit `streamingBehavior`. `!cmd` and `/btw` never enter the outbox; they keep their own paths.
- Uploads attach at dispatch (`uploadAttach`), so an entry keeps its staged uploads only while the daemon's 24 h sweep has not removed them. An entry older than `STAGED_MAX_AGE_MS` with uploads fails with `upload_missing` (O6) instead of sending without them.
- A held entry has no expiry otherwise: it waits for its host. The bubble shows how long it has waited.
- **Recoverable startup.** Storage recovery and pruning must succeed before initialization is latched as started. A transient startup storage failure schedules another attempt without requiring a new send or host hello. Initialize listeners and maintenance once; store shutdown cancels retries and hooks so closed test directories cannot be reopened by delayed work.

### O4. Hand-off to omp's own state

- **Prompt (idle):** the entry is removed when omp's reply to the command has arrived **and** the user message has been echoed (`message_end` with role `user`) on the session channel. The web server sends `outbox_update` without the entry in the same batch as, or after, the echo frame, so a tab never sees neither.
- **Follow-up / steer:** removed when the reply has arrived and a `queue_update` (or a `get_state` snapshot) containing it has been forwarded, or the user message has been echoed (it was delivered at once).
- The `queuedWhileShellRunning` degrade is a follow-up as above.
- **Prompts omp completes without a user message** (builtin or extension slash commands answered with `agentInvoked: false`, which record nothing): removed when the successful reply arrives; no echo is awaited.
- **Uncertain hand-offs require identity evidence.** A message already marked **Not sent** with "may have been sent" must not disappear merely because a queue snapshot or unrelated user message has identical text. Phase 1 has no native message identifier that proves such a match, especially for repeated prompts or upload-only messages. Retain the uncertain entry unless a correlated result proves acceptance or the user explicitly dismisses it.
- **Competing message commands invalidate ambiguous evidence.** An active attempt cannot pair another client's identical echo or queue item with its own reply. Track message admission at the wrapper's actual dispatch seam across all origins; if competing writes make replacement ownership ambiguous, retain the entry with an uncertain outcome rather than retire it. This adds no native message ID, payload marker or long-lived Stop fence.
- **Renew a tainted child, not an uncertain message.** Earlier unresolved admissions may make later replacement evidence ambiguous. Keep their uncertain records and never replay them automatically. Before a separate new idle dispatch, renewal may use the existing awaited child-restart lifecycle only after native `isSettled === true`, no active/background/queued work, no other pending command, dialog or history mutation, a saved session file, and unchanged child/admission generation across preparation awaits. Recheck before teardown, then select the fresh wrapper and recapture mode, queue and history. Settlement and elapsed time alone never confirm the old message. Active work, an offline host or unsupported settlement reporting prevents automatic renewal; Stop remains unfenced.
- **Replacement preserves capabilities.** Before new input reaches a renewed child, restore previously accepted host-tool and URI registrations through their existing registration paths, applying current server policy. Automatic renewal cannot rely on a browser reconnect to restore them.

### O5. Delivery certainty across reconnects and process exits

- Each dispatched command carries the outbox id as `outboxId`. The daemon records, per channel, the outbox ids it has written to the child's stdin (a bounded ring, 256 entries) and reports them in its `hello` (`channels[].delivered`) and in each `res`. This is an added optional field: a compatible link change (`LINK_PROTOCOL_VERSION` 7, `MIN` unchanged). A daemon on v6 or below reports nothing, and the web server treats a lost reply from it as **unknown** (below).
- **Never independently resend what the host link may still replay.** The hub keeps an unacked stdin line in its outbox and replays it after a reconnect (`openLink`, `lib/hosts/hub.ts`). Adding another command creates another transport item, so the dispatcher resends only when refusal proves the first line never entered the transport (503 `delivery: "refused"`). Any uncertain outcome (`delivery: "unknown"` or a timeout) is not independently retried. In phase 2, the daemon also drops repeated `outboxId` values within its retained delivery record. Absence from its bounded ring alone is not proof of non-delivery: an older record may have been evicted.
- **The child exits** before the entry was handed off (O4): no reply or echo will come, so a written entry would sit in **Delivering** for good. The web server marks every in-flight entry of that child **Not sent** with "may have been sent", whether or not its id is in `delivered` (omp may have died before reading the line). Entries still held, not yet dispatched, stay held and go to the next child.
- **Unknown** (a v6 daemon, or a daemon restart, which also kills its children): the entry becomes **Not sent** with "may have been sent; check the transcript". It is retained, never resent automatically, and may be explicitly deleted.
- omp itself has no message id for durable deduplication. A successful stdin write proves neither that omp consumed the line nor that it persisted the message. Only omp's response and the hand-off evidence in O4 confirm acceptance. A daemon record helps avoid duplicate writes; it cannot provide an unconditional exactly-once guarantee across process crashes.

### O6. Failures

- omp refuses the command (validation, unknown command, oversized) → **Not sent** with omp's message.
- The web server refuses `outbox_add` for good (413, authoritatively missing session, 4xx other than 401/408/429) → **Not sent** in the sending browser only; the server did not accept or dispatch that submission. Authentication expiry (401) retains the original scoped entry for re-login; 408, 429, 5xx and network errors are transient too. An undiscovered session whose possible host is unavailable is not an authoritative 404 (O2). The worker keeps transiently refused entries as **Sending** and retries without letting later entries overtake the session's head.
- Nothing goes back into the composer by itself. Phase 1 adds no held-message editing or retry button.
- A deleted session fails its entries; an archived one keeps them held until it is restored.

### O7. Chat ids: omp-web names the conversation, not omp

The outbox needs a key before omp exists for the conversation: a new chat has no omp session until omp starts and writes its header, and today the browser waits for that (`ensureNewSession`, then `promoteNewSession`) before it can send.

- At the first Send of a new chat the composer creates a **chat id** (same generator as the message id). The complete phase-3 command is `{type:"outbox_add",id,scope,mode,message,images?,uploads?,uploadProofs?,chatId,hostId,cwd,provider?,modelId?,toolNames?,thinkingLevel?,advisor?}`: all O2 message fields remain; the chat locator and existing `/api/agent/new` launch fields are additional. `chatId` replaces only the native session ID used to address the command/channel, not the message `id`, replay `scope` or payload. The web server stores the chat (`chats` table: `chat_id, host_id, cwd, launch_config, session_id`) and its entries, and the dispatcher starts the session when the host links (`/api/agent/new` semantics). When omp reports its session id, the server fills `session_id` and publishes it on the chat's channel; the URL and draft key move from the chat id to the session id as `promoteNewSession` does today.
  Snapshot the effective launch choices at Send in IndexedDB and the server's `launch_config`: model provider/id, resolved tool names, thinking level and Advisor. Preserve explicit empty tool lists and `advisor:false`; omission means unset at submission, not permission to read a later browser preference. Validate and apply the stored tool/Advisor spawn settings and model/thinking commands before the first prompt, exactly as the existing new-session route does. Closing the tab, reconnecting or changing preferences afterward must not alter the queued chat's launch configuration.
- An existing session's chat id is its session id. A native ownership move keeps its held entries: retarget their stored canonical session ID during the confirmed identity change, before dispatch resumes. Persist each entry's original source session ID too, so same-ID retries addressed to the old session remain valid after wrapper disposal or a web-server restart; unrelated ID reuse remains refused. In-memory wrapper aliases alone are not durable routing. An ordinary branch or switch does not migrate held entries.
- Whether omp can take a caller-assigned session id (so the chat id *is* the omp id and the mapping disappears) is an open question; the design does not depend on it.

## What this retires

The composer stops being a delivery agent; durable browser and server outboxes take ownership instead:

- **The "deliver after the chat was switched away" exceptions in `handleSend`** (`hooks/useAgentSession.ts`): the startup path that still sends the prompt when the hook unmounted while omp spawned (#389: the `hookAliveRef` / `EventStreamConnectionError` exception, and `AGENTS.md` "A user's prompt is the exception to abandoned readiness"), and, after phase 3, the new-chat `ownerGone` background delivery. With the outbox, Send ends when IndexedDB commits. The worker handles first-leg delivery and the server dispatches once it has stored the message, independently of the composer. The tests become outbox tests (a committed entry survives chat navigation; a server-held entry dispatches with no tab open).
- **The composer's "Sending…" row** and its per-send recovery for messages (`recoverDraft` on refused queue sends, `PromptSubmissionResult.recoveryKey`, the `delivery: "refused" | "unknown"` draft handling).
- **The optimistic user bubble** (`optimisticUserMessage`): held bubbles replace it.
- **The 10-minute `(session, rid)` dedupe for message sends**: `outbox_add` dedupes by message ID for the full bounded browser retry lifetime (O2). The existing dedupe stays for other commands.

Readiness for observing a session (event stream waits, `ensureEventsConnected`) keeps its rules; it now serves display only, never delivery.

## Phases

1. **Server outbox for existing sessions** (O1–O4, O6): store, `outbox_add`, `outbox_update`, dispatcher, held bubbles. Retire the "Sending…" row, the optimistic bubble, the switched-away delivery in `handleSend` (#389) and the composer's per-send recovery. Until phase 2, every lost reply and every child exit with an entry in flight is **unknown** (O5): the entry becomes **Not sent** with "may have been sent", never left in Delivering.
2. **Delivery record on the daemon** (O5): link v7 field and duplicate-write detection. Retrying still requires proof that no earlier attempt can reach omp; a missing bounded-ring record is insufficient.
3. **New chats** (O7): chat ids, server-side session start; retire the `ownerGone` delivery.

## Open questions

- Should Stop (`abort_and_restore_queue`) also withdraw held entries into the composer, as it does omp's queue? Proposed: no, they are not in omp's run yet; Stop leaves them held and they go after the abort as their modes say.
- Inline images in SQLite: up to 5 MB per message base64; acceptable, or move them to the uploads path (As file) when held?

## Not doing
- Editing held messages or changing their delivery mode. The user explicitly excluded these from phase 1; existing omp queue editing remains unchanged.

- Client-only holding (tab memory or `sessionStorage` alone): other tabs would not see the held messages, and a closed tab would lose them.
- Holding beyond what omp offers: no scheduled sends, no reordering of omp's queue.
