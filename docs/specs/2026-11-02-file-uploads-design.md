# Composer file uploads over the links — design

Date: 2026-11-02. Branch: `feat/file-uploads` (on `main` b4e849b4).
Builds on: `docs/specs/2026-11-01-browser-link-design.md` (B2–B5), `docs/specs/2026-10-31-websocket-link-design.md` (D3, D6, D7), `docs/specs/2026-10-28-remote-hosts-design.md` ("Protocol versions and compatibility").

## Why

The composer refuses every file that is neither an image nor text (a `.zip` cannot be attached at all), and images are capped at 5 MB per message. Neither limit comes from omp: omp's RPC stdin has no inbound cap, and omp resizes prompt images itself. The caps are omp-web's own JSON body budget (8 MiB, base64 inline). Files of any type and size up to 2 GiB should reach the agent as files it can read, on the machine where the session's omp runs.

## Decisions

### U1. What the agent gets

- An attached file is written into the session's `local://` root on the session's host: `<sessions>/<project>/<session file minus .jsonl>/local/uploads/<name>`. This is omp's `resolveLocalRoot`; on Windows, a root of 180 characters or more becomes `<tmp>/omp-local/<session id>`, as in omp. A taken name gets ` (1)`, ` (2)`, … before the extension. Names are reduced to one safe path segment (`sanitizeUploadName`, daemon): at most 200 UTF-8 bytes, cut between code points with the extension kept (room is left for ` (n)`); bidi control characters and trailing dots and spaces are stripped; a Windows reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, with or without an extension, any case) gets a `_` prefix.
- Only in that shared Windows fallback, ompweb writes below `uploads/<daemon namespace>/` and returns `local://uploads/<daemon namespace>/<name>`. The namespace is derived from the canonical agent-directory path, so independent daemons do not share retention ownership even when a session file was copied with the same UUID. The native `local://` root is unchanged; ordinary session uploads keep `uploads/<name>`.
- When the prompt is sent, the server appends one block to the message:
  ```
  Attached files (this session's local:// directory):
  - [`local://uploads/data.zip`](/home/u/.omp/agent/sessions/…/local/uploads/data.zip) (/home/u/.omp/agent/sessions/…/local/uploads/data.zip, 12.3 MB, application/zip)
  ```
  The `local://` URL is for omp's tools; the absolute path in the parentheses, exact, is for shell commands. Each URL is a Markdown link (a code span whose fence outruns any backtick run in it) to the percent-encoded path (`encodeURI`, plus `(`, `)`, `#`, `?`, `&`), so the chat opens the file from it whatever the name holds. Chat Markdown keeps Windows drive hrefs (`C:%5C…`, `C:/…`), which the sanitizer would otherwise read as a scheme. Where the chat has no file panel (a remote host's session, whose files main cannot read), a path link renders as its text.
  Local file links handle modified left-clicks in the file panel and suppress middle-click navigation to filesystem paths.
- Limits: 2 GiB per file, 20 files per message.

### U2. What the composer does

- **Images:** each image chip gets an **Inline / As file** switch, Inline by default. Inline is today's path: base64 in the prompt, which omp resizes for the model. As file is the U1 path and keeps the exact bytes. An image that does not fit the inline budget (5 MB per message) is switched to As file automatically, with a notice.
- **Text files** are still inlined while they fit the text budget (4 MB); past it they go As file instead of being refused.
- **Everything else** (archives, PDFs, binaries) goes As file. PDFs are detected by `application/pdf` MIME type or a case-insensitive `.pdf` filename suffix, so an absent browser MIME type cannot send PDF bytes as inline text. The "files skipped" refusals are gone, except for the 2 GiB and 20-file limits.
- Uploading starts on attach. A chip shows progress, then done, or an error with retry. Removing a chip aborts its upload. **Send** waits until every attached upload is done (the button shows the pending count).
- **Automatic resume:** a transient failure (502/503/504, which covers a dropped host link and a stall, or a network error over HTTP, such as a restarting web server) starts the same id again by itself after a back-off of 1, 2, 5, 10, then every 15 s, so it continues from the host's offset in either transport. New bytes on the host end the outage: the next one starts at 1 s again. The chip keeps its progress bar and shows "Reconnecting…" (the failure in its tooltip) until the host answers. Removing the chip ends the wait and aborts the upload on the host over the transport that is live then (`up_abort` only while the worker is still in `ws`, else `DELETE`), not the one of the last attempt. An outage that reaches 5 min (`RESUME_GIVE_UP_MS`, timed from its first failure, so a suspended tab's silence before it does not count) is shown with Retry. Every other failure (4xx, 507) shows Retry at once.
- The remaining five-minute budget bounds both back-off and each in-flight resumed attempt, including HTTP response-body reads. Its watchdog resets only when acknowledged bytes advance, not on a repeated offset. Expiry stops the HTTP request or pauses the WebSocket sender (`up_pause`, scoped to that tab), preserves staged bytes for Retry, and settles with 504 `upload_stalled`. A deadline is checked again after waking and before applying an ack, so a suspended tab cannot revive an expired attempt. Time spent suspended before the first failure still does not count.
- HTTP body-read network failures remain transient just like failures while fetching headers; malformed JSON is not reclassified as a network failure. Chip tooltips use the existing localized network-error explanation rather than the generic upload-failed message.
- An image chip sent As file has no room for the label: while it waits it shows a reconnecting badge (an icon labelled "Reconnecting…") where a failed chip shows Retry, so touch screens see it without a tooltip.
- A draft keeps finished uploads (id, name, size, host); an upload still in flight is lost on reload and must be attached again. Edit-move merges source and destination uploads by id, keeping the first occurrence (source first).
- A page retained in the browser's back/forward cache must not retain an unresolved WebSocket-upload promise after the worker drops its client. Leaving the page fails uploads in flight visibly (410: the worker aborted them on the host); restoring it offers Retry rather than an indefinitely blocked Send. That Retry starts over under a new upload id: the old id's cancel may still be pending in the worker or on its way to the host, and must never reach the new upload. An upload already waiting to resume when the page left keeps its timer and resumes after restoration.
- The target host is the open session's host, or for a new chat the host selected on the new-session screen.

### U3. Staging on the host, attach on send

Uploads go to a staging directory on the target host's daemon, `<agent dir>/omp-web/uploads/<id>.part` plus `<id>.json` (name, size, type, created). They are not written straight into a session because a new chat has no session yet when the file is attached.

1. On send, the prompt command (`prompt`, `steer`, `follow_up`; WebSocket `cmd` or HTTP route alike, so in `runAgentCommand`) carries `uploads: [id, …]`.
2. The server strips the field and calls the host op `uploadAttach {id, sessionFile, sessionId}` for each id. The daemon hard-links the staged file into the session's `local/uploads/` (a copy when the link fails, e.g. on `EXDEV`), deletes the staged one, and returns `{path, url}`. The op's timeout is 10 minutes (a 2 GiB copy across file systems), not the 30 s of other ops.
3. The server then appends the U1 block to `message` and sends the command to omp.

Attachment preparation is part of the wrapper's pending command activity, not idle time. Both cleanup backstops keep the wrapper alive while uploads are attached and the prompt is dispatched, even if no tab is subscribed. A later command awaits the per-session send fence before selecting or replacing the wrapper, not just before dispatch: neither Stop nor an Advisor-triggered child replacement can overtake the attaching prompt. The fence is shared by every registry alias of the wrapper (an omp session move keeps the old id), so a tab addressing the other id waits as well. Preparation failure releases both protections.

The Attached files block is added after the composer's and the route's size checks. If it takes the prompt's host-link `stdin` line past `LINK_LIMITS.maxLineBytes`, the transport refuses it before anything is queued, and the command fails with 413 `request_too_large`. Nothing reaches omp, and the uploads stay registered, so the user can shorten the message and resend.

A failed attach fails the command: 404 `upload_missing`, or 409 `upload_incomplete`. Nothing goes to omp, and the composer keeps the draft. At start and on every `uploadStart` the daemon deletes staged files older than 24 h (`STAGED_MAX_AGE_MS`) and aborts open uploads idle (no start or write) for longer than that, deleting their files; a swept upload gets no `upload_ack`.

A reply to `uploadAttach` can be lost (the link drops after the daemon linked the file). So the daemon keeps a receipt: it atomically replaces `<id>.json` with `attached: {sessionFile, path, url}` and deletes only the `.part`. A retried `uploadAttach` for the same session file, while the target is still a regular file, returns that receipt (one file, no ` (1)` twin); any other session file, missing target or directory target gets 404 `upload_missing`. An `uploadStart` for an attached id with the same name, type and size answers `{received: size, done: true}` only after the same regular-file check; different metadata gets 409 `upload_id_conflict` without replacing the receipt. If receipt publication fails, the newly created target and temporary receipt are removed, the original error is preserved, and the staged source and old metadata remain available to retry. Start, attach and abort controls are serialized per upload id, so a finished abort cannot be followed by an earlier attach recreating its receipt. The 24 h sweep removes receipts like other staged files, without removing files of an active control operation.

### U4. Browser → server (browser link)

The upload id is a client-generated UUID. It doubles as the binary frame id on both links, so the server forwards each chunk without re-encoding it.

| Message | Dir | Seq | Key | Meaning |
|---|---|---|---|---|
| `up_start {id, n, host, name, size, mime}` | ↑ | yes | `up:<id>` | open, or resume, an upload on `host`; `n` is allocated from a worker-wide increasing sequence and is never reused by a Retry, `mime` is the file's type (`type` is the message's) |
| binary `[n][id][payload]` | ↑ | no | `up:<id>` | the next ≤ `pieceBytes` (256 KiB) of the file, in order |
| `up_abort {id, host?}` | ↑ | yes | `up:<id>` | cancel and delete the staged file; `host` (the upload's host, from the tab) reaches an upload the server no longer registers |
| `up_ack {id, received, done, start}` | ↓ | yes | `up:<id>` | the host has written `received` bytes; `done` once all `size` bytes are written and synced. Start replies and asynchronous progress/completion carry the originating `start: n` |
| `up_error {id, status, code, message, start?}` | ↓ | yes | `up:<id>` | the upload failed (host offline, disk full, too large, old host). Failures belonging to a start, including delayed sink errors, carry its `start: n`; malformed messages without a valid generation may receive an untagged error |

- Binary frames are units of the worker's `LinkSender` (it already carries `{id, blob}` items) under key `up:<id>`. A session's commands and replies therefore take turns with upload chunks and never wait behind a whole file.
- **Flow control is end to end.** The worker keeps at most `UPLOAD_WINDOW` = 2 MiB per upload sent beyond the last `up_ack.received`. The server holds no more than that per upload and writes nothing to its own disk: a frame that would put `sent − received` over `UPLOAD_WINDOW + pieceBytes` stops the upload with `up_error` 429 `upload_window_exceeded` (its frames are dropped until the next `up_start`; the socket stays open, and Retry resumes from the host's offset).
- **Resume:** binary frames are not sequenced and are lost when the socket drops. After a resume or resync (a dropped browser link, a web-server restart) the worker sends `up_start` again with the same id and the next `n`; the host answers with its `received` offset, and the worker continues from there. The worker ignores a start answer whose `start` is not its latest `n`, so a replayed or stale answer cannot make it send from a wrong offset.
- **Generation-bound delivery:** each accepted start has its own sink capturing `n`; a queued error or progress event keeps that generation even after a Retry installs a new sink. The worker rejects mismatched generations before changing progress, completing, or failing an upload. Host-attempt filtering alone cannot discard a browser message already queued for an old start.
- **Stall watchdog:** an upload that no start answer or ack advances for `UPLOAD_STALL_MS` = 120 s fails to the tab with 504 `upload_stalled`. The worker forgets it without aborting it on the host, so the tab's automatic resume (U2) starts it again from the host's offset.
- **Host-link drop:** each in-flight upload on that host fails with `up_error` 503 `host_offline`; the tab resumes it by itself from the host's offset once the host is back (U2).
- The tab hands the worker `Blob` slices (`File.slice`, read in the worker) rather than buffers, so the tab holds no file bytes.
- `lib/browser-link.ts` accepts binary frames only for an upload this link started, and only up to `pieceBytes` plus the header. Any other binary frame still closes with 1007. Main forwards a frame only while the sending link's sink is the upload's current sink: after a WS→HTTP handoff (or a newer start) the old socket's late frames are refused, never appended after the offset the new start reported. `BROWSER_LINK_VERSION` stays 1: the worker is served by the same server (content-hashed URL), and an old worker never sends the new types.
- **Durable cancel:** removing a chip, or discarding a finished upload, posts `{op: "up_abort", id, host}` to the worker whatever its mode, and the worker keeps the abort until the server has it (at most 256; the oldest past that is left to the daemon's sweep). In `ws` mode it is an `up_abort` line, queued once the link has a token (the worker dials for it if needed) and kept until the server acks its seq; a resync sends it again. In `sse` mode, and on a switch to it, it is `DELETE /api/uploads/<id>?host=<host>` with a 40 s deadline: a 2xx, or a 4xx other than 408 and 429, settles it; a network error, a timeout, a 5xx, 408 or 429 is retried after 5, 15, then every 60 s and at once on a wake (`online`, `network`, `visible`). Only a tab without a worker sends the DELETE itself, once. A cancel made while offline is lost only if the browser closes before it is delivered, or if the server restarts while it waits for an offline host (main keeps it in memory); the daemon's hourly sweep (U5) then deletes the file once it is 24 h old.

**SSE mode (and the WebSocket fallback)** uses HTTP with the same semantics:
- `POST /api/uploads {id, host, name, size, type}` corresponds to `up_start` and answers `{received}`.
- `PUT /api/uploads/<id>?offset=N` carries a body of up to 1 MiB. The server cuts it into ≤ 256 KiB frames, forwards them, and answers once the host has acked through `N + length`, which is the HTTP form of the window. The final PUT waits for `done: true`, not just `received == size`, so it does not finish ahead of the daemon's final fsync.
- `DELETE /api/uploads/<id>?host=<host>` corresponds to `up_abort` and always answers 204: from there main owns the delivery (U5).

### U5. Server → host (host link v6)

- **Ops:**
  - `uploadStart {id, name, size, type, attempt}` creates the staging file, or opens an existing one, and returns `{received, done}`. Main generates a fresh UUIDv4 `attempt` for every start, including after a registry deletion or server restart.
  - `uploadAbort {id}` deletes the staging file. Main delivers it once the host can take it: an abort that fails 503 `host_offline` or 504 `host_timeout` is kept per host (in memory, at most 1000 per host) and sent again on that host's next hello. A Retry supersedes it: a new `uploadStart` of the same id drops a kept abort, and an abort still in flight is not kept if it fails after such a start registered the id again (the host runs an id's ops in arrival order, so a late abort still lands before the Retry's start). The worker likewise drops its own pending cancel when the same id is uploaded again (U4). An abort for an id main does not register goes to the host the browser named, if that host is known; a registered upload of another owner is never aborted.
  - `uploadAttach` is described in U3.
- **Sweep:** the daemon deletes staged files untouched for `STAGED_MAX_AGE_MS` (24 h) at start, on every `uploadStart`, and every hour (`UPLOAD_SWEEP_INTERVAL_MS`), so an idle host also loses what an undelivered cancel left behind.
- **Down:** binary frames `[n][id][payload]`, the format the daemon already sends up for large results, sent by the hub as `{id, blob}` units of its `LinkSender` under key `up:<id>`. The hub's `flush` learns blob units: a blob unit is sent with the same Bun `send` → `-1` → `drain` handling and is not counted in the line window. The browser's window (U4) bounds it.
- **Up:** `upload_ack {seq, id, attempt, received, done}`, a sequenced line. The daemon queues one after each write, coalesced to at most one per `flushMs` per upload, plus a final one with `done`. Each ack retains the attempt that produced it, even when fair scheduling delivers it after a newer start's reply. Main drops acks whose attempt is not the registry's current attempt before applying progress, completion or errors; only current-attempt acks reach the browser link or HTTP waiter.
- **Daemon writes** at the staged file's current length. A frame for an unknown or finished upload is dropped, and the next `uploadStart` reports the real offset. Bytes beyond `size` fail the upload. A failed attempt remains registered while its write chain removes the old staging files, so a resumed start drains that cleanup before creating or reopening its files.
- **Version:**
  - `LINK_PROTOCOL_VERSION` goes to 6 (new down frames, new up type, new ops). `MIN_LINK_PROTOCOL_VERSION` stays 4.
  - Main uploads only to links with `hostVersion >= 6`. For any other link it answers `up_error` 426: `host_upgrade_required` on a remote host ("Update ompweb on <host> to attach files"), `host_restart_required` on this machine (`local`: "Restart the ompweb host service on this machine to attach files"). After an in-place upgrade the running local daemon keeps its old link version, which is still inside `[MIN, LINK]`, so the upgrade does not restart it.
  - A v5 main closes a v6 daemon with 4426, so the web app is upgraded first, as for every link version (remote-hosts spec, "Protocol versions and compatibility").
- **Daemon errors:** `upload_ack` may carry `error {status, code, message}` (bytes beyond `size`, 507 `upload_write_failed` on a full disk); main turns a current-attempt error into `up_error`. An earlier attempt's error is ignored regardless of whether the replacement start is still in flight or already answered. The UUID attempt check replaces the former in-flight-start timing heuristic.
- **Attach** uses a hard link plus unlink (never overwrites an existing name), falling back to an exclusive copy on `EXDEV`/`EPERM`/`ENOTSUP`/`ENOSYS`. Upload ids stay registered until the prompt reaches omp, so a retried send reuses the earlier attach.
- **Registry on main** (in memory): id → `{hostId, owner, size, received, browser link or HTTP waiter}`.
  - The owner is the browser link's owner (B5); for HTTP it is the same cookie-derived owner (`requestOwner`, `lib/web-auth.ts`).
  - `uploadAttach` requires the same owner and the session's host.
  - Concurrent starts of one id: the latest wins. An older start's host answer still goes to its caller but no longer sets the registry's offset or live state. A start that finds the upload removed (aborted) while it ran sends `uploadAbort` to the host and answers 404 `upload_missing`.
  - At most 32 unfinished uploads per owner; a start past that is 429 `too_many_uploads`. An unfinished entry idle for 10 min (no start, frame or ack) is dropped from the registry to make room; a later `up_start` re-registers and resumes it.
  - A main restart forgets the registry. A finished staged upload then cannot be attached ("attach the file again"); an unfinished one resumes through `up_start`, which re-registers it.
  - Another owner, host, name, MIME type or size for a registered id is 409 `upload_id_conflict`, checked before changing its live state, queued frames, sink or attempt identity. A rejected start leaves the original upload usable.

### U6. Retention of sent uploads

Staged files expire after 24 h (U3), but a sent upload lives in its session's `local/uploads/` for as long as the session does. A web setting, `uploadRetentionDays` in `omp-web-settings.json`, deletes them after a while.

- **Setting:** `number | null`. `null` never deletes. Otherwise a whole number of days, 1 to 3650. The default is 30, matching the media cache's 30-day sweep (`lib/media-cache.ts`); a stored value that is neither reads as 30, and `PUT /api/web-settings` answers 400 `invalid_settings` for one. Settings → System offers Never, 7, 30 and 90 days (a value set through the API shows as an extra choice).
- **Op `setUploadRetention {days}`** (`days`: the setting's value). It is a compatible addition: `LINK_PROTOCOL_VERSION` stays 6, and a daemon that predates it answers 501 `unknown_op`, which main ignores (that host keeps its uploads). Main subscribes to `onHostHello` and immediately sends the setting to already-linked hosts, then sends it on every `hello` and, when the setting changes, to this machine's daemon and every linked host. An offline host (503) gets it at its next hello. Other failures are logged and retried with exponential backoff from 1 s, capped at 30 s, only while linked and the failed value is still current. The daemon validates `days` as the setting is validated (400 `invalid_request`).
- **Daemon:** it stores `days` in `<agent dir>/omp-web/upload-retention.json` (`{"days": …}`, a plain write: the value is not secret, an unreadable file reads as none, and main sends it again at every hello) and answers at once; a value equal to the stored one does nothing, so a daemon that links over and over does not sweep each time. A sweep runs after a change, when the daemon starts (with the stored value; an absent or unreadable file means none yet), and every 24 h from an unref'd timer. A daemon keeps sweeping with its last stored value until main's hello brings the current one, which may differ after a change made while it was offline (a longer stored value deletes later than the setting says, a shorter one earlier). A sweep is idempotent and skips entries that vanish under it, so two at the same time are harmless. It reads the setting again before each delete, so a sweep still running when the setting is made longer, or Never, follows the new value instead of deleting by the old one.
- **Age** is the file's mtime. A hard link shares the staged file's inode, so `uploadAttach` refreshes that inode's mtime before publishing any hard link. A concurrent retention sweep must never observe a new attachment with its old staged age. If stamping fails, no link is published: the bytes go into a freshly and exclusively created file. Cross-device copies use the same fresh-write path: native file-copy operations may preserve old timestamps on Windows. A failed copy removes its partial target and leaves the staged upload retryable; no receipt is published until the copy finishes.
- **Sweep:** for each directory `<sessions>/<project>/<session>/local/uploads/`, the same under the archive (`<archive sessions>/<project>/<session>.jsonl/local/uploads/`: archiving moves the artifacts directory whole), and, on Windows only, `<tmp>/omp-local/<session id>/uploads/<this daemon's namespace>/`, it deletes each regular file whose mtime is more than `days` days old. Whatever else is in that selected folder goes too. The walk has a fixed depth, `lstat`s every entry, and does not follow a symlink it finds: a symlinked project, session, `local`, `uploads` or namespace directory is skipped (uploads under one are never swept: it fails safe), and a symlink, directory or other non-file entry inside the selected folder stays. These checks see each directory as it is when checked; a directory replaced by a symlink while a sweep runs is not caught (Node has no `unlinkat`), and only a process already running as the daemon's user can do that, so it gains no access. A per-entry error is skipped for the next sweep. The uploads folders stay. Staged files are not touched (U3).
  This includes files uploaded through the Files panel into one of those selected session-upload folders; receipt type does not exempt them.
  Directory read failures other than a missing folder (`ENOENT`) are logged with the affected path; the sweep still skips the unreadable folder.
  The daemon serializes each file's `lstat`→`unlink` with every step that puts a file at a name in its own process (attach link or exclusive create, Files-panel publication rename or link). A publication that overwrites an expired file therefore lands either before the stat (and is kept as fresh) or after the unlink; it is never deleted by its predecessor's age. Files-panel publication stamps the staged inode before hard-linking it, as attach does.
- **Windows ownership:** fallback cleanup selects only this daemon's namespace, including after the session was archived or deleted. Session headers alone are not ownership evidence: different agent directories can contain copied UUIDs. Canonicalizing the agent-directory path keeps symlink aliases stable. Legacy flat fallback uploads and other namespaces remain readable but are never automatically deleted. Moving the agent directory changes its namespace; files under the old namespace are preserved rather than reassigned and may need manual cleanup.

## Limitations

- The upload rate is bounded by `UPLOAD_WINDOW / RTT`: about 40 MB/s at 50 ms and 10 MB/s at 200 ms.
- Upload chunks share the host link with session traffic. A Stop can wait for up to one window per active upload to drain on a slow link.
- In-flight uploads do not survive a page reload, and finished ones do not survive a main restart (U2, U5).
- A dropped host link fails every in-flight upload on that host (503 `host_offline`). Each resumes by itself from the host's offset until the outage reaches 5 min; after that it needs Retry.
- If omp moves the session file on its first write, files already attached under the old `local/` root may stop resolving by their `local://` URL (the absolute path still works), and a retried send against the moved `sessionFile` gets 404 `upload_missing`.
- Images sent inline are still resized by omp. Only As file keeps the original bytes.

## Acceptance

1. `npm run typecheck && npm run lint && npm test` and `npm run build` pass.
2. Tests:
   - A chunked upload over a slow browser link does not delay a command reply on the same link by more than a window.
   - A host link dropped mid-upload fails the upload with 503 `host_offline`; a new start resumes from the host's offset, and the attached file matches its SHA-256 (`lib/uploads.test.mjs`, real daemon and link). The browser-link side of a resume (`up_start` sent again on every welcome, a stale `start` answer ignored) is covered by `lib/event-stream-worker.test.mjs` and `lib/browser-link.test.mjs`; the tab's automatic resume in both transports, and that a 4xx or a removed chip does not resume, by `lib/event-stream.test.mjs`.
   - An upload to a v5 daemon fails with 426.
   - `uploadAttach` with another owner's id fails with 404.
   - A taken name gets ` (1)`.
   - A path-traversal name stays inside `uploads/`.
   - Bytes beyond `size` fail the upload.
   - The SSE-mode HTTP path produces the same file.
3. Real smoke (headless Chromium, real omp, local daemon): attach a 300 MB `.zip` and a 12 MB PNG set to As file and send; the agent lists both with `ls` on the absolute path, and the SHA-256 matches. Repeat in SSE mode.
