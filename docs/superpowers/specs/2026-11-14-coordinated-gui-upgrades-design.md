# Coordinated GUI upgrades and legacy-host recovery

## Intent and accepted requirements
Restore application updates from the GUI for binary and npm/bun installations. Include this machine's host in the initial migration. Start a local host automatically when none exists. Upgrade incompatible hosts and the server together after explicit user approval. Keep Settings → Hosts capable of forcing an upgrade even when terminating sessions is necessary. Existing 0.6.0 daemons must be recoverable without an operator logging into each machine.

## Current failure
PR ompweb-dev/ompweb#492 transports the unchanged legacy updater's checkUpdates/updateSoftware requests. The deployed 0.6.0 binary refuses busy hosts, systemd wrappers and the macOS restart-loop supervisor. The new server cannot change those hardcoded decisions by adding a force flag the old daemon does not implement. The server self-updater explicitly rejects standalone binaries. Local bootstrap writes credentials but never starts the daemon.

## Approaches
1. Enable buttons or pass force to the old updateSoftware request: rejected; old code still refuses and false UI promises do not perform upgrades.
2. Require manual SSH/bootstrap on every old host: rejected by the user's requirements; remote execution credentials do not belong in the web application.
3. Use native maintenance updates when available, plus a tightly isolated, explicitly authorized legacy recovery adapter using the historical protocol's existing execution capability. Recommended, subject to verifying the historical execution boundary. Extend the durable update workflow to coordinate server and host transitions.

## Behavior
### Local host
Production startup prepares the existing local token/link and probes the private control endpoint before starting anything. An existing daemon is reused, including an incompatible daemon awaiting recovery. If absent, launch the installed release's host independently of the web server. Reuse the host's singleton lock/control socket; concurrent server starts must not create two hosts. A server restart must not kill the host or its sessions. A service-owned host is not silently replaced with a second foreground process.

### GUI planning and consent
Settings retains server Update and each host's Update. A server update first creates a durable, immutable plan bound to the target release and currently registered hosts. It verifies trusted release identity/digest, application protocol compatibility, management/recovery availability, install ownership, permissions and restart paths. The confirmation shows server/host version transitions, affected hosts and sessions, and whether downtime is required. A distinct Force confirmation explicitly authorizes session termination. Approval cannot be replayed against a different plan or newly changed host inventory. Force bypasses only activity and compatibility coordination restrictions that the recovery mechanism can resolve, never authentication, release integrity, path ownership or process identity.

### Legacy recovery
Keep normal legacy links update-only. A confirmed recovery operation may use the old daemon's existing `open` and `stdin` operations to start one omp process and run a fixed shell bootstrap through its `bash` command. This is an execution capability, not a recovery API the old daemon already understands. Isolation is enforced by the new server: never expose this channel to ordinary session or application traffic. Historical 0.6.0 builds share a daemon protocol number but use different runner envelopes; verify the RPC-form and runner-form commands against immutable real builds rather than assuming the version identifies the envelope.

Bind `launch.creationId` and the helper's exclusive on-disk lock to the durable recovery operation so retries cannot start independent migrations. Stage a server-pinned, digest-verified helper and candidate, preflight them, and detach the helper outside the process tree/service cgroup being replaced before any stop. Validate the daemon and supervisor's ownership and process identity, stop the supervisor before the daemon when necessary, retain its verified restart command across the in-place replacement, and restart the release. Retain and restore the previous installation and supervisor on failure.

Do not trust shell output as completion: extensions can replace it. Success requires the expected new daemon's authenticated reconnect and a matching operation receipt. After rollback, the old daemon's existing `checkUpdates` operation exposes the durable worker result; no second execution channel is needed. A rejected or failed bootstrap is reported as failure, never success. The local host uses its private control endpoint and same-machine recovery worker rather than requiring a working old runner or a public bootstrap helper.

Before implementing this adapter, prove on scratch real historical v10 and v11 installations that the bootstrap executes and its detached helper survives closing its session and stopping the old daemon. Verify Linux systemd cgroup escape, the macOS restart-loop and Windows process-tree behavior separately. Do not claim support from a mocked supervisor or a POSIX-only script. A drained old daemon, an existing updater operation, a broken omp runner, missing bootstrap tools or insufficient service permissions can prevent remote execution. Such failures must remain visible, with no false success and no incompatible server cutover that destroys recovery. If the historical protocol cannot execute the required recovery, report the exact failed boundary before revising the design.

### Modern managed hosts and force
Use the independently versioned maintenance API for inventory, update preparation, commit/status and recovery acknowledgements. Ordinary updates do not kill sessions. Force updates stop sessions only after staging/preflight and explicit confirmation. Recognized binary services/supervisors have an explicit verified restart contract; arbitrary wrapper command lines are not treated as trusted scripts. The local host is a first-class participant, not an exception hidden from the GUI.

### Coordinated server update
Extend the current durable prepare/commit/status workflow rather than adding a second updater UI. Restore standalone-binary updates using existing bounded release download, digest, archive validation and preflight logic. Package updates keep their existing manager convention. The coordinator persists approval, the verified candidate and per-host operation identities. A restarted server resumes an interrupted host phase without another approval or a second host operation; the cutover worker runs detached and continues while the server stops. For compatible releases it avoids unnecessary host/session restarts. For hard incompatibilities it stages all required artifacts and obtains approval before committing a coordinated transition. No server-only cutover may strand a registered incompatible host without a verified recovery path. Health receipts must prove the expected release, runner preflight and authenticated maintenance identity; mere socket connection is not success. Retain previous installations until the whole plan completes. If rollback cannot restore the previous state, report which participants require recovery rather than claiming atomic success.

## Verification
Use actual historical 0.6.0/0.7.0 binaries or immutable sources with their original updater, not a reimplementation. Exercise Linux systemd direct and wrapped services, the macOS supervisor shape and foreground/binary/package installations. Verify normal busy refusal and explicit forced session termination, rollback, no duplicate host on cold start/concurrent starts, missing local host, service process identity changes, changed candidate/plan, archive/digest failures, disconnected hosts, partial coordinated failures and recovery after server interruption. Verify actual Settings → Hosts and server-update confirmation/progress in a browser against a scratch deployment. Never force-upgrade the live session as a test.

### Windows acceptance
Windows is a first-class implementation target, not a POSIX simulation. Use native PowerShell/.NET process and service/task APIs for bootstrap, detached recovery, process-identity verification, replacement of a running `.exe`, restart and rollback. Preserve Windows paths, quoting and the current user's private control descriptor. Test actual Windows processes and binary installs on the existing `windows-latest` CI lane; setting `process.platform` in Linux tests is insufficient. Include foreground, service/task-supervised, initial local bootstrap, normal/forced host updates and coordinated server cutover. No mandatory Unix utilities on Windows.

### Initial feasibility result
On this Linux host, the actual deployed historical `0f09049ea1c3` binary reported ompweb 0.6.0/protocol 10 in a scratch HOME. Its real runner accepted a recovery-only `bash` command; a helper started with `systemd-run --scope` and its own session survived explicit recovery-channel termination and daemon SIGTERM, then wrote its expected result. This proves the Linux execution/detachment boundary only, not a complete migration or Windows/macOS support.

## Scope and risks
No new dependency or SSH integration. No full legacy application adapter. No removal of integrity/authorization checks. A forced live upgrade can end this session; implementation and scratch verification do not authorize executing it on production. Offline hosts cannot be reported upgraded; an update without an established recovery path remains blocked. Windows behavior must use its process/service semantics rather than Unix signals.
